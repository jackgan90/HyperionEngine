# 开发质量审计

本 skill 协调主 agent 与独立 reviewer。Reviewer 提供有证据的发现，主 agent 对复核、修复范围和最终结论负责。创建或编辑本 skill 本身不等于要求审计整个工程。

## 确定审查对象

主 agent 先确定本次任务目标、用户要求的行为与约束、额外审查重点，以及可定位的代码版本。用户后续补充的重点也要传给 reviewer；把它作为待验证的关注点，不预设缺陷或结论。

- 给出仓库绝对路径、已解析的基线 commit、目标 commit 或工作区快照，以及相关文件。审查未提交改动时，应覆盖相关的 staged、unstaged 和新增文件，并说明与本次任务无关的已有改动。
- 保留用户已有改动。Reviewer 读取共享工作区期间，主 agent 不修改被审查的文件；可独立阅读调用链、检查证据或整理验证方案。需要并行改代码时，先提供可读取的固定快照。
- 根据任务提供必要的模块关系、复现入口、构建/测试命令、环境限制和原始日志。已运行的检查只是参考证据，不能替代 reviewer 自己核对代码。
- 让 reviewer 从该仓库读取适用的 `AGENTS.md`、`docs/CodingStyle.md`，以及需要时的 `docs/SourceLayout.md`、`docs/VisualStudio.md`。遵循当前规范对建议和例外的弹性，不自行升级为硬性缺陷。

## 创建独立 reviewer

使用 `collaboration.spawn_agent`，明确设置 `fork_turns: "none"`，通过 `message` 发送自包含的审查简报。不使用默认继承上下文的方式，不复制会话记录、主 agent 的推理过程或预期审核结论，也不复用参与过本次实现的 agent 作为首次 reviewer。

Reviewer 工作期间，主 agent 可基于原始需求和代码做自己的核查；不要把“主 agent 认为实现正确”作为 reviewer 的前提。若工具无法创建无上下文继承的 reviewer，应明确报告独立审核未完成，不能把自审称为独立审核。

简报应包含以下信息，并替换成当前任务的实际内容：

```text
你是独立 reviewer，只负责审核，不直接修改自有代码，也不再创建下一级 reviewer。
仓库与审查版本：仓库绝对路径、基线、目标/快照、相关文件与排除项。
任务目标与验收要求：用户要求实现或保持的行为、约束和范围。
用户补充重点：原始关注点及必要说明；没有补充时明确说明。
必要背景：模块关系、入口、运行条件和适用规范所在位置。
可用证据：复现步骤、检查命令、原始日志；注明未验证项和环境限制。

独立阅读改动及其直接相关的调用链，核对任务是否达成、是否存在行为回归或明确的规范违反。
可做非破坏性的复现和必要验证，生成物放在仓库 out 下，不改源码或 Git 状态。
每项 finding 给出 ID、优先级、文件和具体行号、触发条件、预期与实际行为、影响及证据。
区分已验证缺陷、待验证疑点和可选建议；说明问题是否由本次改动引入、是否在任务范围内。
不要为凑数量报告猜测或个人偏好。未发现可确认缺陷时直接说明，并列出检查范围和未验证部分。
```

读取 reviewer 的最终结果；没有报告、审查中断或验证受限都不等于“通过”。

## 主 agent 独立复核

对每项 finding，主 agent 应自行读取当前版本的相关代码，核实触发条件和调用路径，并用复现、针对性测试或可核对的静态推理验证缺陷。只重复 reviewer 的说法或照用其建议不算复核。

记录复核结论及依据：

- **确认**：证据支持缺陷存在，说明它与本次任务的关系。
- **不成立**：给出代码、规范或验证结果作为反证，不因 reviewer 的措辞或优先级而接受。
- **待确认**：明确缺失的证据和下一步验证；不能把未能复现直接当作误报，也不能为了关闭 finding 就修改代码。

Reviewer 的修复建议同样需要判断，不能直接照搬。对于超出审查范围但有明确证据的问题，记录影响和范围关系，不悄悄扩大任务。

## 修复范围与停止条件

先对已确认的 findings 评估最小可行修复及其影响。用户明确要求只审查时，报告结论和修复建议，不自动改代码。

用户允许修复且仍在当前任务范围内时，主 agent 自行完成最小化修复；不为顺手优化扩大改动，也不对这些已授权的小修复重复请求确认。按问题实际影响选择验证，优先复用现有测试；需要回归测试时覆盖触发条件，不机械增加测试。

**如果确认修复需要大规模重构，或者明显超出当前任务范围，主 agent 必须暂停自动修复，先总结现状并向用户确认下一步。** 不因问题优先级高或 reviewer 强烈建议而越过此边界，也不要先实施重构再征求同意。

结合任务判断规模：例如需要重设模块职责、改变公共契约或持久化协议、重写资源生命周期，或大范围修改无关调用方。不要只用文件数或行数作机械阈值；已授权的统一符号改名可以涉及许多文件。

触发停止条件后，保留已完成的改动，可继续只读核查。向用户说明已确认的问题、影响、当前完成情况、可行方案与取舍，以及为何需要扩大范围；请求用户对具体下一步作决定。得到答复前不继续依赖该决定的修复。

## 验证与收尾

范围内修复完成后，让原独立 reviewer 对更新后的代码、原 finding 的触发条件和直接影响做针对性复审。提供新的可定位版本和原始验证结果，不只告知“已经修好”。如需更换 reviewer，仍使用 `fork_turns: "none"` 并重新给出必要简报。

对复审中新发现的问题沿用“主 agent 复核 → 判断范围 → 修复或暂停”的流程。不要为了追求无边界的完美扩大审查，也不要在没有新改动或新证据时反复跑全套检查。

最终汇报审查版本和范围、用户重点覆盖情况、各 finding 的复核与处置、实际验证结果，以及未解决问题或待用户决定的事项。把“未发现缺陷”“修复已验证”和“尚未完成验证”准确区分，不将独立审核等同于没有任何风险。
