## 发现与处置

### BP-02 / P1：字节压力使稳定计划反复重建

旧实现将强持实例数值的准备记录与完整实例块放在同一字节池中。准备记录被淘汰后，计划的弱身份在 `CurrentInputs` 释放时过期；下一帧重新准备全部输入，再次淘汰，形成循环。普通 Device/Order 回退也会付这个成本，即使它不需要实例 payload。

独立探针使用精确基线源码重新编译全部 60 个 Renderer 翻译单元，配合同版头文件、相同未变更依赖与同一 harness。每轮 40 次预热、100 个测量样本，输入构造和逐项覆盖检查在计时之外。

| 触发条件 | 基线 | 审计前候选 | 计划复用 |
| --- | ---: | ---: | --- |
| Debug，默认 16 MiB，2048 稳定项 | 3.2251 ms | 142.5677 ms | 100/100 → 0/100 |
| Release，64 KiB，1024 项 Device 回退 | 0.08680 ms | 0.67090 ms | 100/100 → 0/100 |
| Release，64 KiB，1024 项 Order 回退 | 0.08701 ms | 0.70577 ms | 100/100 → 0/100 |

以上为三轮均值。默认 Release 的 2048 项没有触发这个循环，不能把问题泛化为所有配置均退化。原始证据保留在 `probe-debug`、`probe-release`，未覆盖或删除失败版本的数据。

修复将准备记录改为弱值身份证明，不再拥有数值树，按 `MaxItems` 限制数量。当前强值的 owner 和地址相同可直接证明命中；需要比较不同值对象时先 `lock()` 保活。旧的非空值过期不能等于空值，缓存值地址不被解引用。完整块与既有 record/block 缓存继续执行实例字节预算，轻量计划身份不会随字节压力消失。

`CachedInputs` 表示准备记录数量；`CachedInputBytes` 是准备对象、页游标与弱值数组的结构性估算，未计 map/list 节点、分配器开销及弱引用保留的 make_shared 分配。`CachedBytes` 才是受 `MaxBytes` 限制的实例缓存计费值；这些指标均不代表整个 Renderer 的内存占用。

**处置：已关闭。** 独立 reviewer 在 `probe-fixed-debug`、`probe-fixed-release` 以相同 harness 重跑三轮 A/B。每种配置、每个重点场景的修复后 300 个测量帧均复用计划，准备数据重建为零。主 agent 核对原始 CSV、覆盖检查和源码调用链，确认原循环消失。

| --- | ---: | ---: | ---: |
| Debug，2048 稳定项 | 3.013201 | 3.659832 | +21.46% |
| Debug，64 KiB Device 回退 | 1.230358 | 1.284853 | +4.43% |
| Debug，64 KiB Order 回退 | 1.224064 | 1.318011 | +7.68% |

### BP-01 / P2：插入失败后 LRU 与索引失配

新准备缓存先创建 LRU 节点，再向 map 插入。如果 map 分配抛出 `std::bad_alloc`，外层会捕获异常，但 LRU 节点没有撤销。以 `MaxItems=1` 的 A/B/C 输入为例，A 的 map 插入失败、B 成功后，C 淘汰 A 时会把 `end()` 交给 `ErasePrepared`，产生无效解引用风险。

主 agent 独立核对了插入、异常捕获、后续淘汰调用链。定点注入仅在 out 中的同版源码副本进行，在实际无效解引用前记录并中止；原日志为 `InvalidPreparedEraseCount=1`。该证据不依赖真实系统 OOM 或偶然崩溃。修复为 map 插入失败时回滚刚创建的 LRU 节点，再传播异常。

**处置：已关闭。** 原 reviewer 用当前同版源码副本和同版 Renderer 库重跑注入，`allocation-fault-fixed/Run.log` 为 `InvalidPreparedEraseCount=0`；后续再次 Build 的数量及字节预算断言也通过。主 agent 核对注入仍位于生产 map 插入处，修复实际执行了 LRU 回滚，未通过绕过触发点隐藏问题。

旧 Items/Chunks 存在相近插入形式，本 finding 限于本次新增 Prepared 路径，没有扩大到其他缓存的统一重构。

### 共享更新固定开销

追加三轮原版冻结 EXE 对比确认 Release shared 从 0.117884 ms 增到 0.129116 ms（+9.53%）。新 `FPlanItem::Matches` 在同一 resolved、共享覆盖变化时，会再次进入 `MatchesValues` 重复身份校验。修复在这个已证明局部值相同的分支直接比较实例值，并保留 `bInSharedRefresh` 对自定义策略的保守限制。

修复后独立探针三轮均值：Release 为 0.107104 → 0.110094 ms（+2.79%），Debug 为 1.608333 → 1.807857 ms（+12.41%）。计划仍每轮 100/100 复用；固定成本没有完全消失。这与完整规划器基准的共享更新结果分开记录，不选择性保留较好的测量。
